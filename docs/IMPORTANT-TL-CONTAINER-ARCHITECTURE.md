# ★ 중요 설계 문서 — TimeLink 범용 상호 인증 컨테이너 아키텍처

> **상태:** 설계 기준안 (구현·보안 검증 전)
>
> **적용 저장소:** `Taolee-crypto/timelink-frontend`
>
> **목표:** 기존 미디어 디코딩 엔진을 활용하면서 파일 컨테이너와 플레이어 컨테이너의 상호 인증으로 디지털 자산의 권리·이용 조건을 통제한다.

---

## 0. 문서의 지위와 용어

이 문서는 현재 확정된 제품 방향과 앞으로 검증해야 할 기술 설계안을 구분한다. 여기서 설명하는 목표 구조를 이미 구현되었거나 보안 검증이 끝난 기능으로 간주해서는 안 된다.

- **파일 컨테이너(File Container):** 미디어 페이로드와 자산 식별·권리·시간·무결성 정보를 하나의 논리적 자산으로 묶는 포맷.
- **플레이어 컨테이너(Player Container):** 기기·플레이어 식별, 인증 키, 자산 검증, 권한 확인 및 실행 엔진 연결을 담당하는 신뢰 실행 구성요소.
- **어댑터(Adapter):** 인증이 끝난 페이로드를 해당 형식의 기존 디코더 또는 뷰어에 전달하는 형식별 연결 모듈.
- **서버 기준 레코드:** 자산 등록 시 서버가 보관하는 식별자, 해시, 권리정보, 컨테이너 버전 및 상태.
- **상호 인증:** 파일 컨테이너의 진위·무결성과 플레이어의 등록·상태를 각각 검증하고, 그 결과를 동일한 세션에 묶는 절차.

이 문서에서 '컨테이너'는 암호화된 오디오를 뜻하지 않는다. 보호의 중심은 컨테이너의 진위, 권리 메타데이터, 인증정보, 세션 및 이용 권한이다.

## 1. 설계 전환

### 1.1 기존 접근

기존 TL3 계열은 오디오 또는 오디오 세그먼트를 암호화하고, 재생 과정에서 서버·클라이언트가 키와 복호화 절차를 수행하는 구조를 사용해 왔다. V5에는 전체 컨테이너 암호화, 기기별 키 교환 및 세션 라이선스 등 기존 구현이 존재한다.

### 1.2 새로 검토하는 접근

새 방향은 MP3 페이로드를 암호화·복호화하는 것을 기본 전제로 삼지 않는다.

1. MP3 페이로드는 MP3 형식으로 유지한다.
2. 페이로드에 자산 식별, 시간정보, 권리 메타데이터, 무결성 증거를 결합한다.
3. 이 결합을 파일 컨테이너로 표현한다.
4. TimeLink 플레이어 컨테이너가 파일 컨테이너와 서버를 상호 검증한다.
5. 검증 성공 후에만 해당 형식의 어댑터가 페이로드를 기존 디코더에 전달한다.
6. 재생 권한, 횟수 및 정산은 서버가 관리한다.

**중요:** 페이로드를 암호화하지 않는다면 컨테이너에서 페이로드를 분리하거나 추출하는 것을 암호학적으로 막을 수 없다. 이 설계의 보호 대상은 권리 컨테이너의 위조·변조·재사용 및 권한 없는 TimeLink 이용이다. 오디오 자체의 기밀성이나 추출 불가능성을 주장하지 않는다.

## 2. 시스템 구성

### 2.1 파일 컨테이너

논리적 구성은 다음과 같다.

| 필드 | 목적 | 검증 주체 |
|---|---|---|
| Magic / format version | TLNK 형식과 버전 식별 | 플레이어 |
| Asset ID | 자산의 고유 식별 | 서버 |
| Media kind / codec | 음악·영상·문서 등 유형과 포맷 | 플레이어·서버 |
| Payload length | 페이로드 경계 확인 | 플레이어 |
| Payload digest | 페이로드와 등록 자산의 동일성 확인 | 서버·플레이어 |
| Duration / timeline | 재생시간 또는 시간축 정보 | 서버 |
| Rights manifest | 창작자, 이용 조건, 라이선스 참조 | 서버 |
| Creator attribution | 창작자 및 공동 창작자 귀속 | 서버 |
| Container nonce / revision | 발급본 구분 및 재발급 관리 | 서버 |
| Signature | 정식 발급 및 매니페스트 무결성 검증 | 플레이어·서버 |

서명 대상은 모호한 JSON 문자열 연결이 아니라, 필드 순서와 인코딩이 고정된 canonical representation이어야 한다. 서명에는 최소한 포맷 버전, Asset ID, 미디어 유형, 페이로드 길이와 해시, 시간정보, 권리 매니페스트 해시, 발급 버전 및 nonce를 포함한다.

### 2.2 플레이어 컨테이너

플레이어 컨테이너는 다음 기능을 가진다.

- 고유 Player ID 및 구현 버전 식별
- 기기별 키 쌍 보관 및 개인키 비추출 저장소 사용 가능 여부 확인
- 서버 인증 및 세션 생성
- 파일 컨테이너 서명·해시·정책 검증
- 재생 권한과 이용 횟수 확인
- 형식별 어댑터를 통한 기존 디코더 연결
- 재생 이벤트와 서버 정산 결과의 일관성 확인

브라우저 환경의 JavaScript만으로는 강한 변조 방지나 비추출 실행환경을 보장할 수 없다. 웹 플레이어는 웹 환경에 맞는 위협 모델을 적용하고, 더 강한 기기 신뢰가 필요한 플랫폼은 OS 보안 저장소 또는 네이티브 구성요소를 별도 검토한다.

### 2.3 서버

서버는 자산 및 권한의 신뢰 기준점이다.

- 자산 등록과 기준 해시 보관
- 권리 매니페스트와 서명 검증
- 플레이어·기기 등록 및 폐기
- 세션 nonce 발급과 재전송 방지
- 이용 권한·횟수·만료 확인
- 재생 이벤트 수신 및 TL 정산
- 비정상 요청, 재사용, 버전 폐기 탐지

서버 비밀키와 서명키는 클라이언트에 배포하지 않는다. 키 회전·폐기·유출 대응 절차를 마련한다.

## 3. 상호 인증 및 재생 프로토콜

권장 논리 흐름은 다음과 같다.

1. 사용자가 TL 자산을 플레이어에서 연다.
2. 플레이어는 컨테이너 헤더와 매니페스트를 읽되, 아직 디코더에 페이로드를 전달하지 않는다.
3. 플레이어는 Asset ID, 컨테이너 버전, 페이로드 해시, Player ID, 플레이어 버전 및 기기 공개키 식별정보를 서버에 제출한다.
4. 서버는 등록 자산의 기준 레코드와 비교하고 자산 상태 및 사용자 권한을 확인한다.
5. 서버는 세션 ID, 만료시각, 일회성 nonce 및 서명된 권한 응답을 발급한다.
6. 플레이어는 기기 개인키의 소유를 증명한다. 서버는 등록된 공개키로 이를 검증한다.
7. 서버 응답은 자산 ID, 플레이어 ID, 사용자 ID, 세션 ID, nonce, 권한, 만료시각 및 허용된 정책에 결합된다.
8. 플레이어는 응답 서명과 모든 결합 필드를 검증한다.
9. 검증 성공 시에만 형식별 어댑터가 페이로드를 기존 디코더 또는 뷰어에 전달한다.
10. 세션 종료·중단·완료 이벤트를 서버에 전달하고 서버 기준으로 이용 기록 및 정산을 확정한다.

상호 인증은 단순히 두 파일에 동일한 문자열이나 고정 키를 넣는 방식으로 구현하지 않는다. 서버가 발급하는 nonce, 세션별 응답, 기기 키 소유 증명 및 서명된 권한 응답을 이용한다. 모든 요청은 Asset ID·Player ID·User ID·Session ID에 결합되어야 한다.

## 4. 기존 플레이어 및 디코더와의 호환

### 4.1 호환 원칙

기존 MP3 디코딩 엔진을 재사용하되, 기존 플레이어가 수정 없이 TL 컨테이너를 인식한다고 가정하지 않는다.

지원 방식은 플랫폼별로 나뉜다.

- **소스 수정형:** 오픈소스 플레이어의 파일 로더 앞단에 TL 컨테이너 판독·인증 모듈을 추가한다.
- **플러그인형:** 공식 플러그인 API가 제공되는 플레이어에 어댑터를 설치한다.
- **전용 래퍼형:** 기존 디코딩 라이브러리를 내부에서 호출하는 TimeLink 플레이어를 제공한다.
- **브라우저형:** 웹 플레이어가 컨테이너를 검증한 후 Web Audio, MediaSource 또는 지원되는 디코딩 경로로 전달한다.

### 4.2 보안 경계

인증 모듈을 우회해 일반 플레이어로 페이로드를 직접 열 수 있다면, 그 페이로드는 기술적으로 일반 MP3와 동일하게 취급될 수 있다. 따라서 컨테이너 인증은 TimeLink 서비스 이용 권한을 통제하지만, 평문 페이로드 추출 자체를 막는 DRM으로 표현해서는 안 된다.

플레이어 패치가 실제 보안 경계가 되려면 파일 열기 경로, OS 파일 연결, 플러그인 로딩, 캐시 및 임시 파일 처리까지 구현별로 점검해야 한다.

## 5. 자산 유형별 어댑터

공통 컨테이너와 공통 인증 절차를 유지하고, 페이로드 해석만 유형별 어댑터로 분리한다.

| 자산 유형 | TimeLink 유형 | 페이로드 예 | 어댑터 |
|---|---|---|---|
| 음악 | TL3 | MP3 등 | Audio Adapter |
| 영상 | TL4 | MP4 등 | Video Adapter |
| 문서 | TLD | PDF 등 | Document Adapter |
| 이미지 | 유형 확장 검토 | JPEG, PNG 등 | Image Adapter |

모든 유형이 동일한 시간 기반 과금 정책을 사용하는 것은 아니다. 음악·영상은 재생시간 기반 정책을 적용할 수 있고, 문서·이미지는 창작자가 정한 이용 조건을 적용할 수 있다. 앨범 묶음 TLJ는 여러 자산의 관계를 표현하는 상위 패키지로 별도 정의한다.

## 6. TL 재생 권한과 정산

현재 제품 규칙을 보존한다.

- 기준 단가: 1초 = 1 TL.
- 곡별 충전은 해당 곡의 재생 가능 횟수를 확보하는 방식이다.
- 곡의 필요 TL을 충전하면 그 금액에 해당하는 재생 가능 횟수가 확보된다.
- 재생 시작 시 확보된 재생 가능 횟수를 소비한다.
- 실제 재생시간 정산은 1초당 1 TL 원칙을 따른다.
- 중도 정지와 완주 정산은 기존에 검증된 규칙을 유지한다.
- 재생 횟수 소비와 시간 정산이 중복 청구되지 않아야 한다.
- 본인 자산의 자기 재생에는 창작자 자기 보상을 지급하지 않는다.

이 문서는 정산 알고리즘을 재설계하거나 기존 정상 작동 코드를 변경하도록 승인하지 않는다. 컨테이너 전환과 정산 변경은 분리한다.

## 7. 위협 모델과 시험 계획

### 7.1 방어 대상으로 삼는 위협

- 컨테이너 매니페스트의 무단 수정
- 페이로드를 다른 자산으로 교체
- 창작자 또는 권리정보 위조
- 유효하지 않은 컨테이너 발급본 사용
- 플레이어 ID 또는 기기 인증 위조
- 세션 응답 재전송
- 만료·폐기된 권한 재사용
- 허용되지 않은 자산·사용자·플레이어 조합
- 재생 횟수 및 정산 이벤트 중복 제출

### 7.2 보장하지 않는 사항

- 암호화하지 않은 페이로드의 추출 불가능성
- 인증된 재생의 외부 녹음·캡처 완전 차단
- 사용자가 디코더에 접근할 수 있는 환경에서의 모든 메모리 추출 방지
- 변조 가능한 브라우저 JavaScript 자체의 완전한 신뢰성

### 7.3 필수 테스트

| 시험 | 기대 결과 |
|---|---|
| 매니페스트 한 바이트 변경 | 서명 검증 실패 |
| 페이로드 교체 | 해시 불일치로 거부 |
| 다른 Asset ID로 재사용 | 서버 기준 레코드 불일치 |
| 다른 플레이어 ID로 응답 재사용 | 세션 결합 검증 실패 |
| nonce 재사용 | 재전송 탐지 및 거부 |
| 만료 세션 사용 | 거부 |
| 폐기된 기기 키 | 거부 |
| 잘못된 어댑터·코덱 | 안전하게 실패 |
| 정상 인증 및 재생 | 기존 디코더에서 정상 재생 |
| 중도 정지·완주 | 기존 TL 정산 규칙과 일치 |

## 8. 개발 순서 및 변경 통제

### 1단계 — 현행 V5 기준선 보존
- 현재 정상 재생·인증·재생 횟수·정산 경로를 기록한다.
- V5 관련 파일과 API 계약을 백업하고 기준 커밋을 고정한다.
- 새 설계 실험은 별도 모듈 또는 별도 브랜치에서 수행한다.

### 2단계 — TLNK 컨테이너 규격 확정
- 바이너리 레이아웃, canonical manifest, 해시 범위, 서명 알고리즘, 버전 정책을 문서화한다.
- MP3 페이로드의 실제 경계와 메타데이터 영역을 명확히 구분한다.
- 호환성·확장성·파일 손상 검출을 시험한다.

### 3단계 — 파일 컨테이너 검증기
- 서버 기준 레코드, 서명, 해시 및 권리정보 일치 검증을 구현한다.
- 인증 실패 시 디코더 호출이 발생하지 않는지 테스트한다.

### 4단계 — 플레이어 컨테이너와 상호 인증
- 플레이어 등록, 기기 키, nonce, 세션 결합 및 폐기 기능을 구현한다.
- 위조·재전송·만료 테스트를 통과시킨다.

### 5단계 — MP3 어댑터
- 기존 MP3 디코딩 엔진을 유지한다.
- 검증 성공 후에만 페이로드를 전달한다.
- 일반 플레이어 우회 및 임시 데이터 노출 경계를 점검한다.

### 6단계 — 정산 통합
- 기존 재생 가능 횟수와 TL 정산을 그대로 연결한다.
- 별도 회귀 테스트 후 통합한다.

### 7단계 — TL4·TLD 확장
- 공통 컨테이너·인증 계약을 재사용한다.
- 각 형식의 어댑터와 권한 정책만 추가한다.

## 9. 완료 판정 기준

다음 조건을 모두 충족하기 전에는 새 구조가 완성되었다고 선언하지 않는다.

1. 컨테이너 규격이 버전 관리되는 문서와 테스트 벡터로 고정되어 있다.
2. 파일 컨테이너의 서명·해시·권리정보 검증이 자동화 테스트를 통과한다.
3. 플레이어의 기기 키 소유 증명과 세션 결합이 통과한다.
4. 인증 전 디코더가 페이로드를 받지 않는 것이 확인된다.
5. 정상 인증 후 MP3가 기존 엔진에서 연속 재생된다.
6. 중도 정지·완주·재시도에서 기존 재생 횟수와 TL 정산이 회귀하지 않는다.
7. 재전송·변조·만료·기기 폐기 시험이 통과한다.
8. 구현·배포·실서비스 검증 결과가 각각 별도로 기록된다.

## 10. 설계 결정 요약

TimeLink의 범용 디지털 자산 아키텍처는 **미디어 페이로드 암호화 중심이 아니라 파일 컨테이너와 플레이어 컨테이너의 상호 인증 및 서버 권한 검증 중심**으로 검토한다.

오디오·영상·문서 등 원본 페이로드는 각 형식의 기존 실행 엔진을 활용한다. 공통 컨테이너는 자산 식별, 시간·권리 메타데이터, 무결성 및 발급자 인증을 제공하고, 플레이어 컨테이너는 기기·실행환경 인증과 이용 권한 확인을 담당한다.

이 설계는 창작자의 권리정보와 서비스 이용 권한을 지속적으로 관리하는 것을 목표로 한다. 비암호화 페이로드의 추출을 막는다고 주장하지 않으며, 실제 보안 범위는 위협 모델과 시험 결과로 입증한다.

**개발 우선순위: TL3 파일 컨테이너 → 플레이어 컨테이너 → 상호 인증 → 기존 MP3 엔진 연동 → 정산 회귀 검증 → TL4/TLD 확장.**
