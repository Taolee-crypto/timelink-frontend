# TimeLink V5 영업·매출·재무·정산·세금 통합 설계

기준일: 2026-10-26, 한국시간. 한국 운영 법인: (주)틸로코리아.

이 문서는 영업관리·매출관리·재무관리의 공통 거래 연결과 정산·세무 처리를 정리한 개발 기준안이다. 확정된 사업정책, 제안된 운영 방식, 법률·계약 검토가 필요한 사항을 구분한다. 문서 저장은 화면·API·은행 송금·세금 신고 구현 완료를 의미하지 않는다. 세무 항목은 아래 공식 자료를 확인한 일반 기준이며 개별 계약의 세무 판정을 대신하지 않는다.

## 0. 영업관리·매출·재무는 같은 거래를 공유한다

사용자 추가 확정 지시: 매출과 재무와 영업관리는 서로 연결되어 있어야 한다. 각 메뉴는 하나의 사업 거래를 서로 다른 관점에서 조회·처리하는 화면이며, 별도 독립 장부를 만들어 같은 매출·보수·세금을 다시 기록하지 않는다.

| 업무 화면 | 담당 정보 | 같은 거래에서 연결되는 값 |
| --- | --- | --- |
| 영업관리 | 매장·상점주·매니저·DJ·계약·정책·유료 전환·실적 귀속 | 스토어 ID, 회원 ID, 역할·계약·연결 버전, 원거래 ID |
| 매출관리 | 실제 제공 서비스, 무료·유료 출처, 공급가액·VAT, 취소·환불, 매출 인식 | 서비스 이용 ID, TL 차감 원장 ID, PG 영수증·증빙, 매출 전표 ID |
| 재무관리 | 은행·PG 입금, 선불 의무, 파트너 미지급금, 원천세·VAT, 승인·지급·납부·대사 | 원화 전표 ID, 정산번호, 지급 요청·결과 ID, 신고·납부 번호 |

거래 흐름은 ‘회원·매장·담당자 연결 → 실제 결제 또는 서비스 사용 → 무료·유료 출처 확인 → 매출·의무 인식 → 매니저·DJ 배분 → 원화 평가·세무 판정 → 승인·지급 → 신고·납부 → 대사·마감’이다. 결제·매출 인식·보수 지급·세금 납부는 서로 다른 사건이므로 날짜와 금액을 분리하되 같은 원거래로 추적한다.

### 공통 거래의 연결 키

운영 법인·국가·통화·시간대, 원거래 ID, 충전 결제 ID, 서비스 이용 ID, TL 경제원장 거래 ID, 스토어 ID, 상점주 회원 ID, 매니저 회원 ID, DJ 프로필·회원 ID, 계약·담당 연결 버전, 정책 버전, 매출 인식 ID, 원화 회계 전표 ID, 배분 명세 ID, 정산번호, 수취인 세무 프로필 버전, 지급 요청·결과 ID, 증빙·취소·역분개 ID를 연결한다. 정산번호는 여러 원거래의 명세를 묶을 수 있고, 하나의 충전은 여러 서비스 사용에 배분될 수 있으므로 모든 것을 단일 결제번호 한 칸에 우겨 넣지 않는다.

### 화면 간 이동

스토어 상세 → 해당 매장 매출 원거래 → 원거래의 TL 차감·매니저/DJ 배분 → 해당 정산서 → 원화 전표·세금 → 실제 입금·지급·납부 증빙으로 이동할 수 있어야 한다. 반대로 재무의 지급 건에서도 정산서·대상 매장·당시 매니저·DJ·계약까지 거슬러 확인할 수 있어야 한다. 목록의 기간·법인·국가·매장·담당자 필터를 상세 이동 시 유지한다.

### 대시보드에서 구분할 숫자

현금 수납액, PG 미수금, 미사용 유료 TL의 원화 의무, 가입 선물 발행량, 서비스 사용에 따른 공급가액 매출·매출 VAT, 매니저 발생 보수, DJ 발생 보수, 지급 가능·보류·실지급액, 미지급금, 원천세 예수금·납부액, 회사 비용과 손익을 각각 표시한다. 총 충전액을 매출로, 플랫폼 배분 몫을 순이익으로, 가입 선물 발행량을 현금 수익으로 바꿔 표시하지 않는다. 서로 단위가 다른 TL·TLC·원화를 합산하지 않는다.

회원이 100,000TL을 유료 충전한 뒤 여러 매장에서 사용하는 경우 충전 수납은 한 번, 각 서비스 사용과 취소는 개별로, 파트너 보수는 해당 서비스와 당시 담당자에게 귀속되게 한다. 무료 선물 사용이면 그 사실과 실제 서비스 이용은 추적하지만 유료 파트너 배분을 만들지 않는다. 1% 고객 보너스도 원래 매장 결제·상점주 부담·고객 지급에 연결하되 이를 플랫폼 서비스 매출로 중복 가산하지 않는다.

### 재무·영업 통합 대사

유료 충전·환불·차지백의 실제 영수증을 PG·은행과 맞추고, TL 유료 잔액의 원화 의무·서비스 사용·조정을 대사한다. 매니저/DJ의 확정 보수는 미지급금·정산서·실지급·기납부 세금과 대사한다. 취소와 환불은 원거래에서 관련 매출·배분·미지급금·세금·영업 실적에 정정 이벤트로 전파하고 과거 행을 조용히 덮어쓰지 않는다. 비동기 반영에는 처리 대기·실패·재처리 상태와 중복 방지 키를 둔다.

회계 전표와 원장을 자동으로 기록하는 범위는 검증된 계약·세무 정책이 마련된 유형에 한정하고, 미확정 거래는 검토 대기로 남긴다. 영업 정책 조정 권한으로 세금 신고 결과나 은행 잔액을 수정할 수 없도록 권한을 분리한다.

## 1. 어드민 대메뉴는 ‘영업관리’

| 하위 메뉴 | 관리 대상과 책임 |
| --- | --- |
| 영업 현황 | 국가별 유치 매장, 무료 체험, 유료 전환, 활성·중단 매장, 실제 거래 기반 실적 |
| 영업 매니저 | 가입 신청, 서명 계약, 입금 확인, 승인·정지, 담당 매장, 매니저 실적 |
| 파트너 DJ | 자격·활동 상태, 연결 매장, 방송 실적, 계약, DJ 배분 내역 |
| 스토어 | 상점주, 매장 페이지, 담당 매니저·DJ, 서비스 상태, 무료·유료 사용, 고객 보너스, PoC |
| 수익 배분·정산 | 원거래별 배분, 대상자별 정산서, 지급 가능·보류, 승인, 지급 결과 |
| 세금·증빙 | 수취인 세무 분류, 부가세, 원천세·지방세, 세금계산서·영수증, 신고·납부·제출 현황 |
| 영업 정책 | 가입비, 가입 선물, 서비스 요금, 배분 기준, 보너스율, 적용 시점과 변경 이력 |

영업관리의 ‘세금·증빙’은 기존 재무·회계 모듈의 같은 거래와 세무 프로필을 조회하는 업무 화면이다. 영업용 세무 장부를 별도로 중복 생성하지 않는다. DJ의 방송 제작·송출은 DJ 스튜디오에서 수행하고 영업관리에서는 파트너 관계·매장 연결·정산을 관리한다. TILO 중앙방송 운영·권리자 보상은 별도 사업 흐름이다.

## 2. 관리의 중심은 스토어 한 곳의 관계도

스토어에는 상점주 회원, 담당 매니저 회원, 파트너 DJ 프로필과 그 회원, 서비스 계약, 정책 버전, 원거래·정산 내역을 연결한다. 매장 상세에서 세 사람과 거래를 볼 수 있고, 매니저·DJ 상세에서도 연결된 매장으로 이동할 수 있게 한다.

매니저 변경은 상점주 요청을 기준으로 처리한다. 기존 계약·연결 버전과 효력 시각을 보존하며, 변경 이후 발생한 거래에 새 담당자를 적용한다. 관리자가 정산을 승인한다고 담당 매니저를 임의로 바꿀 수 있게 만들지 않는다. 계약 예외 처리에는 별도 권한·사유·근거를 남긴다.

## 3. 확정 사업정책과 미확정 조건

상점주는 무료 가입한다. 기존 42,500TL과 추가 57,500TL을 합쳐 총 100,000TL을 가입 선물로 준다. 중복 지급을 막고, 선물을 소진한 이후 구매한 TL로 서비스를 이용하는 단계부터 매니저·DJ 배분이 발생한다. 매장 서비스비의 50%는 매니저·DJ 공동 배분 재원, 50%는 플랫폼 몫이다. 이 서비스비에서 창작자 몫을 추가 배분하지 않는다.

매니저 25%·DJ 25%는 공동 재원을 반반 나누는 제안이다. 가입비 10만 원 역시 제안이며 확정액으로 자동 적용하지 않는다. 모든 수치는 관리자 수동 설정·정책 버전·효력 시각·변경 이력을 갖게 한다.

회원의 매장 소비에는 실제 결제액의 1%를 즉시 사용 가능한 TL_P로 준다. 5,000원 결제의 예시는 50TL_P다. 보너스 부담금 예치·차감 방식은 제안 단계다. 선물 잔액이 실제 유료 재원으로 바뀌거나 무료 서비스 사용에서 지급 가능한 수익이 만들어지지 않도록 출처를 보존한다.

## 4. 정산 금액은 세 단계로 구분

1. 서비스 이용 TL과 무료·유료 출처를 확인해 배분 대상 TL을 산정한다.
2. 원거래 시점 정책과 담당자 연결 버전으로 매니저·DJ·플랫폼 몫을 확정한다.
3. 지급 권리와 환전 조건이 확인된 TL에 한해 계약상 기준으로 원화 금액을 평가하고 세금·증빙을 반영해 지급액을 확정한다.

TL 수량을 원화 금액으로 그대로 복사하지 않는다. 고객 보너스의 1원=1TL 예시는 모든 TL 정산의 고정 환전율을 뜻하지 않는다. 창작자 기여도별 현금 환전율도 매니저·DJ 지급에 임의 적용하지 않는다.

**반드시 확정할 계약 항목:** 서비스비의 배분 기준에 부가세·PG 수수료를 포함할지, 정산 보수에 부가세가 포함인지 별도인지, TL 지급의 권리 내용과 원화 평가율, 환불·상계 조건. 현재의 50% 사업 원칙은 유지하되 ‘세금 공제 후 50%’ 등으로 조용히 바꾸지 않는다.

매장 서비스비를 플랫폼이 자기 책임으로 제공한다면 총액 매출과 파트너 비용을 검토하고, 대리인이라면 수수료 순액 인식을 검토한다. 플랫폼 배분 50%를 회계상 순이익으로 표시하지 않는다. 서비스 책임·계약과 회계기준에 따른 본인·대리인 판단은 회계 검토 사항이다.

## 5. 회원별 세무 프로필

회원의 역할과 세무 유형은 별도 필드다. 같은 사람이 매니저와 DJ를 겸해도 회원은 하나이고, 정산 명세는 역할·계약·소득별로 분리한다. 서로 다른 소득을 한 세율로 합산하지 않는다.

필수 항목은 수취인 법적 명의, 개인·개인사업자·법인 여부, 거주지국과 세법상 거주자 여부, 사업자 유형과 부가세 구분, 계약별 소득 종류, 증빙 종류, 원천징수 대상 여부·국세율·지방세율·적용 기간, 검토자와 근거 문서, 본인 명의 지급 계좌다. 주민등록번호·외국 납세번호·계좌 정보는 법정 수집 근거와 필요 범위를 확인해 보호하고 목록 화면에는 마스킹한다.

사업자등록만으로 원천징수 유무를 결정하지 않는다. 실제 용역과 소득 종류, 고용관계, 면세 요건, 거주성에 따라 판단한다. 미분류는 ‘세금 0원’이 아니라 ‘판정 대기’다.

3.3%는 해당 유형의 지급 단계에서 징수하는 금액이며 수취인의 최종 종합소득세를 확정하는 세율이 아니다. 세율과 적용 대상은 지급시점 법령 기준으로 확인하고 시행 전 개정안과 현행 세율을 혼합하지 않는다.

### 계산 예시 — 단위는 원화, 환전율 예시가 아님

| 경우 | 보수·세금 계산 | 수취인 지급액 |
| --- | --- | --- |
| 원천징수 대상 인적용역 사업소득, 부가세 면세 요건 확인, 보수 1,000,000원 | 소득세 30,000원 + 지방소득세 3,000원 | 967,000원 |
| 필요경비 60% 적용이 확인된 일반 기타소득, 과세최저한 미해당, 대가 1,000,000원 | 소득금액 400,000원 × 20% = 80,000원, 지방세 8,000원 | 912,000원 |
| 원천징수 비대상으로 확인된 과세 용역, 공급가액 1,000,000원에 VAT 별도 | 부가세 100,000원, 적격 증빙 확인 | 1,100,000원 |

부가세 포함 총액 1,100,000원이 계약 금액이면 공급가액은 1,000,000원, 부가세는 100,000원이다. 표시된 파트너 몫에 부가세를 추가로 얹을지는 계약의 포함·별도 규정으로 판단한다. 위 3개 예시를 매니저·DJ·법인에 이름만 보고 배정하지 않는다. 절사·반올림은 세목별 법정 규칙과 증빙을 기준으로 정한다.

## 7. TL·TLC의 세금 발생 시점

‘현금 출금할 때만 과세’라고 일괄 설계하지 않는다. TL 보수가 사용·양도·상계 가능한 권리로 확정되는 시점, 실제 지급, 서비스 재사용, TLC 전환 등 각각의 거래 실질과 원화 시가 평가를 검토해야 한다. 내부 적립 확정일·사용 가능일·세법상 지급일·송금일을 별도 저장한다.

세금이 발생하는 TL 지급이라면 원천세를 현금으로 납부할 재원과 지급 방식도 계약에 마련해야 한다. TL을 일부 차감했다는 사실만으로 국세·지방세 납부 완료로 표시하지 않는다. 미확정 보수나 단순 PoC 점수를 곧바로 과세 소득으로 단정하지도 않는다.

고객의 구매 보너스, 상점주의 판촉 부담금, 매니저·DJ의 용역 보수, 창작자 사용료, TLC 채굴과 처분은 서로 다른 성격이다. 하나의 ‘보상세’나 일괄 원천세로 합치지 않는다. 특히 TLC의 채굴·수령·교환·처분은 거래 유형·당사자·적용시기별 별도 세무 검토 항목이며 여기서 단일 세율을 정하지 않는다.

## 9. 정산서에 보여줄 값

정산번호, 귀속기간, 세법상 지급일, 지급 법인·국가, 회원·역할·계약·스토어, 원거래와 취소·조정, 무료·유료 출처, 배분 대상 TL, 적용 배분율·정책 버전, 담당자 연결 버전, 정산 TL, 현금 지급 대상 TL, 원화 평가 기준·시각·근거, 공급가액·부가세, 원천징수 기준액·국세·지방세, 기지급액·기납부 세액, 정당한 상계와 사유, 이월·보류, 실지급액, 계좌, 승인자, 지급 결과, 신고·납부·제출 접수번호를 표시·연결한다.

내부 사용 전용 TL, 현금 지급 가능 TL, 보류 TL을 나눈다. 플랫폼 몫은 파트너 지급액과 같은 의미의 출금 신청 대상으로 만들지 않고 회사 매출·비용·세금으로 관리한다. 보상용 PoC는 정산 통화와 별도 지표로 표시한다.

## 10. 정산 처리 순서와 마감

원거래 수집 → 무료·유료·취소 대사 → 담당자·정책 버전 확인 → 배분 확정 → 세무 프로필·증빙 확인 → 지급일과 원화 평가 확인 → 세액·실지급액 계산 → 관리자 검토·승인 → 실제 지급 → 은행·PG·TL·미지급금 대사 → 세금 신고·납부 및 소득자료 제출 → 월 마감.

각 단계의 상태는 ‘집계 중 / 증빙 대기 / 세무 검토 / 승인 대기 / 지급 예약 / 지급 중 / 지급 완료 / 지급 실패 / 신고 대기 / 신고 완료 / 납부 완료 / 마감’으로 구분한다. 지급 완료가 세금 납부 완료를 뜻하지 않는다. 미분류·증빙 누락은 해당 건만 보류하고 세금 0원이나 지급 완료로 넘기지 않는다.

월별 집계·검토 후 다음 달 15일 지급하는 일정은 운영안으로 둘 수 있지만 아직 확정하지 않는다. 이미 TL의 사용 가능 시점에 세법상 지급이 발생하는 구조라면 그 지급일 기준으로 신고 기한을 산정한다. 조회 월·귀속 월·실제 지급 월을 혼합하지 않는다.

국세 원천세는 일반적으로 지급월 다음 달 10일까지 신고·납부한다. 적법한 반기납부 등 예외는 별도 설정한다. 거주자 지방소득세 특별징수도 일반적으로 징수월 다음 달 10일까지 납부한다. 해당 거주자 사업소득 간이지급명세서는 지급월 다음 달 말일까지 매월 제출하며, 매월 모두 제출하면 연간 지급명세서 제출 면제 여부를 확인해 적용한다. 기타소득은 법정 세부 유형에 맞는 자료와 주기를 따로 선택한다. 공휴일·신고기한 특례는 실제 달력에 반영한다. [S2][S6][S7]

신고 자료 생성과 홈택스·위택스 제출, 제출과 납부, 지급 요청과 은행 송금 성공은 각각 별도 확인한다. 신고·납부·송금 영수증이 없는 상태를 완료로 표시하지 않는다.

## 11. 정정·권한·중복 지급 방지

원거래·수취인·역할·정산 기간·정책 버전 기반 고유키와 지급 요청 키를 둔다. 같은 요청 재실행은 기존 결과를 반환하고 중복 지급하지 않는다. 매니저 변경은 과거 정산을 다시 지급하는 이유가 되지 않는다.

원장 확정은 삭제·덮어쓰기 대신 취소·역분개·보상 거래로 정정한다. 환불·이의제기·연결 변경·원천세 재분류에는 원거래와 정정 사유를 남긴다. 이미 신고·납부한 건은 수정 신고·소득자료 정정 여부까지 추적하고, 이미 사용한 TL 보수나 원천세를 조용히 재차 차감하지 않는다.

영업 담당자는 연결·실적을, 재무 담당자는 세무 분류·정산 검토를, 지급 승인자는 확정 지급을 처리한다. 세율·계좌·세무 프로필 변경과 지급 승인·송금 권한을 분리할 수 있게 한다. 초기 운영에서는 관리자가 수동 통제하고 모든 변경을 기록한다.

## 12. 기존 코드와의 차이 및 구현 순서

기준 코드: frontend 05707630a8613e822b8d4b7ed86b14f3ff8ff9c5, backend ae05c701b78dbd8f08dc5f7085bfbc46b2b3e931.

1. admin.html의 영업 매니저·DJ·카페방송 관리가 서로 다른 메뉴·데이터 경로로 나뉘어 있다. ‘영업관리’의 하위 메뉴로 재구성하고 스토어 연결을 공통 조회해야 한다.
2. 기존 스토어 화면이 호출하는 /api/admin/cafe/channels는 확인한 백엔드에 정의가 없다. 실제 관리자 권한의 스토어 조회 API와 연결해야 한다.
3. loadCafeMgmt는 반환값 없는 paginate 호출에 .join을 붙여 오류가 발생한다. 활성 수 × 50,000TL을 월 수익으로 표시하는 임의 계산도 실제 원거래 집계로 교체해야 한다.
4. DJ 관리의 dj_cafe_links는 예전 매칭·DJ/카페/플랫폼 배분 정보를 표시한다. 새 v5_sales_stores·v5_sales_payments 및 정책 버전과 대조해 현행 관계·배분과 구분해야 한다.
5. src/kr-finance.ts는 원화 전표·세금 프로필·원천세 예상 계산·월 마감의 기반이다. 현재 지급 템플릿은 creator_payable 및 저작자 기타소득 유형 중심이므로 매니저·DJ에 이름만 바꿔 재사용하면 안 된다. 역할별 미지급금·계약별 소득 유형·부가세·증빙·지급시기를 확장해야 한다.
6. 실제 TLC·TL 정산과 원화 전표·세금 신고·은행 지급을 하나의 정산번호로 연결한다. 외부 신고·송금은 기존 계산 API가 대신 실행한 것으로 간주하지 않는다.

검증에는 무료 사용 배분 0, 1원 단위 예시 계산, 서로 다른 수취인 세무 유형, VAT 포함·별도, 동일 회원 역할 겸임, 담당 변경, 취소·부분 환불, 중복 재시도, 동시 지급, 송금 실패 재처리, 미분류 보류, 마감월 정정, 이미 신고한 건의 정정, 비거주자 미확정 차단, 관리자 권한, 원장·은행·세액 합계 일치를 포함한다.
